## Why this isn't a copy-paste job

Production and staging turned out to be built on two different systems:

| | Production (synnovatia.com) | Staging (synnovatiacom.stage.site) |
|---|---|---|
| Theme | Twenty Nineteen Child | Synnovatia Child (GeneratePress-based, block-theme/Site-Editor capable) |
| Page builder | Elementor Pro (Theme Builder, Loop Grid, Loop Items, Archive templates) | GenerateBlocks + GenerateBlocks Pro (native Gutenberg blocks, incl. a dynamic "Query" block) |
| Elementor installed? | Active, in full use | Installed but **inactive** — Elementor Pro can't even activate ("unmet requirements") while core Elementor is off |

Confirmed by checking the live `/about/` page on staging with Elementor deactivated — it renders fully styled, meaning the real redesigned pages (homepage, About, Work With Me, etc.) were built in GenerateBlocks, not Elementor. Jackie chose to rebuild the blog natively in GenerateBlocks to match, rather than reactivating Elementor just for this and importing the production templates.

**Real bug found and fixed mid-build (layout regression):** at some point the flex-row Container ended up empty while the Image and content Group sat outside it as plain top-level siblings, which stacked them vertically instead of side-by-side. GenerateBlocks' empty-container appenders and direct clipboard-paste-onto-a-selected-block both proved unreliable (paste always *replaces* the selected block rather than appending) — the reliable fix was: select the non-empty sibling already inside the target container (Image), use the top-toolbar Block Inserter to insert a *fresh empty* Group as a new sibling in the same parent, then select that fresh empty Group and paste the clipboard content — paste replaces the empty placeholder in place, keeping the correct position. This pattern (insert-empty-sibling-via-toolbar, then paste-to-replace) is the reliable way to move a fully-built block into a specific container slot in this editor going forward.

**Two more real bugs found and fixed while verifying on the live front end** (both invisible in the block editor canvas, only visible on the actual published page):
1. **Button text invisible** — text and background were both teal. Root cause: GenerateBlocks' external CSS file (Settings → CSS Print Method) doesn't regenerate automatically on save; fixed via Settings → "Regenerate CSS Files," which is now a required step after any pattern style change before checking the live front end.
2. **Post title rendered in the theme's default green underlined link style instead of navy Fraunces**, even after adding `!important` to the Headline block's own class. Root cause: GenerateBlocks' Headline block puts its class on the wrapping `<h2>`, not on the inner `<a>` it generates when a link is set — so an inherited (even `!important`) ancestor color always loses to the theme's unstyled-but-more-specific `a { color; text-decoration }` rule matched directly against that `<a>`. Also could not be diagnosed via `getComputedStyle()` from JS on a `:visited` link, since browsers deliberately report the unvisited color to scripts for privacy even when painting a different one — pixel/screenshot inspection was required instead. Fix: added explicit `& a { ... !important }` rules (plus `& a:visited` / `& a:hover`) in the Headline block's CSS Mode, rather than relying on the block's own top-level Typography styling. **Any future GenerateBlocks Headline/link-wrapping block in this build should get this same `& a {...}` treatment up front**, not just a color set on the block itself.

**Two real bugs found and fixed along the way:**
1. **`generateblocks/query-page-numbers` requires being nested *inside* the `generateblocks/query` block**, not placed as a sibling — it has an `ancestor:["generateblocks/query"]` restriction and consumes pagination state via block context (`generateblocks/queryId` etc.) that only flows to descendants. First attempt placed it as a sibling in an outer wrapper and it silently rendered nothing (no error, just blank). Fix: nest it alongside the `looper` block, both as children of the `query` block.
2. **Card images rendered wildly oversized (331px tall instead of ~176px)** on a post with a portrait-oriented photo, badly misaligning from the topic tag (top) to the CTA button (bottom) — flagged by Jackie directly, twice (the first fix attempt wasn't actually right — see below). Root cause: the Blog Post Card pattern's image only had `width:176px` set, no `height`, so `object-fit:cover` had nothing to crop against and the image rendered at its natural aspect ratio.
   - **First attempt — fixed height (`height:176px`)**: made every image a uniform 176×176 square. This solved the oversized-image case but broke the *other* direction — cards with longer titles/excerpts now had a real text column taller than the fixed image, leaving a gap between image-bottom and button-bottom (this is what Jackie's second screenshot caught, on the old `Preview: Growth & Scaling Archive` page).
   - **Second attempt — flexbox `align-items:stretch` + image `height:100%`**: matches the *prose description* of the original 2026-08-19 fix, but measuring all 8 cards showed it wasn't actually stretching — image height varied 115–222px independent of row height, gaps up to ~100px. This is a known, genuinely unreliable corner of flexbox: percentage heights on flex children don't reliably resolve against an auto-height flex container, especially for replaced elements like `<img>` with their own intrinsic aspect ratio.
   - **Real fix — switched the row from `display:flex` to `display:grid`** (`grid-template-columns:176px 1fr`), image `width:100%; height:100%; object-fit:cover`. CSS Grid pre-computes definite row-track heights before laying out children, so a percentage height on the image reliably resolves — flexbox doesn't do this for an auto-height container. Re-measured all 8 cards on the Growth & Scaling preview page: 7/8 at an exact 0px gap, 1/8 with a 22px *under*-fill (a tall source photo setting the row height, with that particular card's shorter text not reaching all the way down) — a minor, normal editorial-card imperfection, nothing like the original 70–330px overflows. Applied once to the shared pattern (post 11896), so it fixed every place the pattern is used at once — verified no regression on `/topic/mindset-resilience/` (live topic archive) and the new front page's Cover Story card.
   - **Real GenerateBlocks quirk hit while fixing this:** the block has a separate cached `css` attribute alongside its `styles` attribute — updating `styles` via `wp.data.dispatch` alone did nothing live, because GenerateBlocks reads the stale pre-compiled `css` string for both the saved block markup and the external stylesheet, and that string only normally recomputes through the Style panel's own UI interaction. Had to update both attributes together, every time. Separately, confirmed (again) that "Regenerate CSS Files" only rebuilds a given compiled file on that *specific* file's owning page's next load — regenerating while viewing an unrelated page does nothing for other pages' cached CSS files; had to specifically reload page 11852 (the page whose CSS file happens to be the canonical one all pages reference for this pattern's classes) to force the real rebuild, every time the pattern changed.

**Two real bugs hit rebuilding this, both worth remembering for any future custom dynamic block on this site:**
1. **A custom `css` override on a block replaces its entire compiled stylesheet, not just adds to it.** Giving a title block a `css` string with only its `a{}`/`a:hover{}` link-color rules silently dropped every rule that would normally have been auto-generated from its `styles` attribute (font, size, color, margin) — the block rendered with zero styling. Any block that needs a custom `css` override must have that override include the *full* rule set, not just the delta.
2. **GeneratePress's theme CSS beats same-or-lower-specificity page CSS even on the element the class is directly applied to**, not just nested links — this was already known for the *inner* `<a>` tag of a dynamic-tag-generated title, but this time the *outer* h2's own `color` property also lost to the theme default despite a matching class selector, and a plain button `<a>` element's `color` lost the same way even with no nesting involved. Every text color set via a custom block in this build now needs `!important`, not just link-wrapped ones.

Also re-confirmed (twice) that the "image looks completely missing" symptom is consistently just the `lazysizes` library not having fired yet at screenshot time — scrolling the element into view and re-checking resolves it every time; not worth chasing as a bug anymore.

**Eighth request, Jackie-initiated (2026-08-23): full-bleed Cover Story.** She asked for the Cover Story row specifically (image + navy panel) to extend edge-to-edge across the full browser width, breaking out of the page's normal ~1120px contained column — a deliberate design choice, not a bug fix.
